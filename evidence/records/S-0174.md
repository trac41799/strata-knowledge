The canonical statement of chaos engineering practice, authored by engineers who
built Netflix's Chaos Engineering team. Web-verified: defines chaos engineering
as "the discipline of experimenting on a system in order to build confidence in
the system's capability to withstand turbulent conditions in production"; the
basic method is a four-step experiment (1. define "steady state" as a measurable
output indicating normal behavior; 2. hypothesize the steady state will continue
in both control and experimental groups; 3. introduce variables reflecting real
world events such as servers that crash, hard drives that malfunction, network
connections that are severed; 4. try to disprove the hypothesis by looking for a
difference in steady state between the groups); "the harder it is to disrupt the
steady state, the more confidence we have in the behavior of the system"; the
advanced principles are: build a hypothesis around steady state behavior, vary
real-world events, run experiments in production, automate experiments to run
continuously, and minimize blast radius. Verification note: the practice's
origin — Netflix's Chaos Monkey (2011), which randomly terminated production
instances, later expanded into the Simian Army suite — is documented by the
Netflix Tech Blog post "The Netflix Simian Army" (Izrailevsky & Tseitlin, 19
July 2011) and by Wikipedia's Chaos engineering article, which the chaos-monkey
claim in `operations/incident-response` relies on.
